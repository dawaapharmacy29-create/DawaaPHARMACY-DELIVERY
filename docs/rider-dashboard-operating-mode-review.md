# Rider Dashboard Operating Mode — مراجعة وتنفيذ آمن

## الفرع الآمن

تم تنفيذ التعديلات الأولية على الفرع:

`rider-dashboard-ui-final-safe5`

بدون تغيير مسار `/rider` الحالي وبدون تعديل أي RPC أو قاعدة بيانات.

## الملفات المضافة

1. `src/components/rider/RiderOperatingDashboard.tsx`
   - مكوّن واجهة تشغيل جديد للمندوب.
   - يعرض حالة الشيفت، البطارية، الإنترنت، GPS، الأوردرات المفتوحة، والمزامنة.
   - يستقبل callbacks جاهزة من الداشبورد الحقيقي بدون أن يعرف تفاصيل Supabase.

2. `src/pages/rider/RiderOperatingPreview.tsx`
   - صفحة معاينة آمنة للتصميم الجديد.
   - لا تسجل بيانات حقيقية ولا تستدعي RPC.
   - المسار: `/rider-operating-preview`.

3. `src/lib/riderDeviceSnapshot.ts`
   - helper مشترك لقراءة البطارية وحالة الاتصال وتجهيز بيانات audit.
   - الهدف لاحقًا استخدامه مع: تسجيل الأوردر، تم التسليم، فشل التسليم، الحضور، والانصراف.

4. `src/App.tsx`
   - تمت إضافة lazy route جديد فقط:
   - `/rider-operating-preview`
   - لم يتم تغيير `/rider`.

## المشاكل التي ظهرت أثناء مراجعة الكود

### 1. الداشبورد الحالي كبير جدًا

ملف `RiderDashboard.tsx` يحتوي على آلاف السطور ويجمع وظائف كثيرة جدًا في ملف واحد:

- الحضور والانصراف.
- تسجيل الأوردر.
- OCR الريسيت.
- المشاوير.
- تعديل الأوردر.
- فشل التسليم.
- التنبيهات.
- السياسات.
- Realtime.
- Offline جزئي.

هذا يزيد خطر كسر وظيفة موجودة عند أي تعديل مباشر كبير.

الحل الآمن:
- نقل الواجهة الجديدة إلى مكوّن مستقل.
- دمج المكوّن تدريجيًا مع نفس الدوال الموجودة.

### 2. البطارية موجودة لكن غير مركزية

يوجد مكوّن `RiderDeviceMonitor` يقرأ البطارية ويرفعها إلى `rider_device_status`.

لكن البطارية ليست ظاهرة كحالة أساسية أعلى الداشبورد، وليست مرتبطة بوضوح بكل عمليات الأوردر والتسليم.

الحل المقترح:
- إبقاء `RiderDeviceMonitor` كما هو.
- استخدام helper `readRiderDeviceSnapshot` داخل عمليات مهمة لاحقًا.

### 3. Offline Queue غير مكتمل للأوردرات

يوجد Offline Queue عام ومرتبط بالمشاوير، لكن تسجيل الأوردرات يرفض العمل Offline حاليًا لأن إنشاء الأوردر يتم عبر RPC آمن.

الحل المقترح:
- السماح بحفظ أوردر Offline كـ pending_local فقط.
- لا يتم احتسابه إلا بعد المزامنة الناجحة عبر RPC.
- إضافة `idempotency_key` لمنع التكرار.

### 4. زر تم التسليم يحتاج audit أقوى

الواجهة الحالية تستدعي RPC لتأكيد التسليم.

المطلوب لاحقًا:
- قراءة GPS قبل التسليم.
- قراءة البطارية قبل التسليم.
- إرسال snapshot للسيرفر أو تخزينه في audit.

### 5. احتمال خروج المندوب للوجين عند خطأ تحقق مؤقت

يوجد منطق تحقق من الجلسة جيد، لكن يجب الحذر من مسح الجلسة عند أخطاء شبكة/Supabase مؤقتة.

الأفضل:
- لا يتم مسح الجلسة إلا إذا رجع السيرفر صراحة `valid=false`.
- لو حدث خطأ شبكة، يتم الاحتفاظ بالجلسة وعرض تحذير.

## خطة الدمج التالية

### المرحلة 1 — مراجعة التصميم

افتح المسار:

`/rider-operating-preview`

وتأكد أن شكل الصفحة مناسب للمندوب.

### المرحلة 2 — تركيب المكوّن داخل `RiderDashboard.tsx`

بعد الموافقة على الشكل:

- نستبدل الجزء العلوي من الداشبورد الحالي بمكوّن `RiderOperatingDashboard`.
- نمرر له نفس الدوال الحالية:
  - `handleCheckInOut`
  - `setActiveModal('order')`
  - `openOrders('pending', 'الأوردرات المفتوحة')`
  - `setActiveModal('trip')`
  - `loadAll(true)`
  - `handleDeviceLogout`

### المرحلة 3 — تقوية audit

استخدام `readRiderDeviceSnapshot` قبل:

- `handleDelivered`
- `handleFailed`
- `handleSaveOrder`
- `handleSaveEditOrder`
- `handleCheckInOut`

### المرحلة 4 — Offline للأوردرات

إضافة local pending order queue بطريقة لا تحتسب الأوردر إلا بعد sync.
